## 学习内容

用户复述要点（按题）：

1. **角色**：BullMQ 是中间仓库 / broker；接 客户端请求后「尽最大可能把 Job 推送给设备网关执行并获得反馈」。
2. **Queue 与 Worker 分开 + 持久化**：解耦后任一环节宕机能保住 Job；临时性宕机可通过重连恢复；持久化避免只存内存的风险，系统重启后尽可能恢复数据。
3. **什么时候用 / 不用**：适合「需要稳定传递、确保送达、不需要大批量回放」；不适合「团队语言不是 Node/TS」以及「海量事件、需要回放和分区级顺序」。
4. **没有 Redis / 只需内存异步**：直接用进程内队列。
5. **相邻技术**：Kafka 主攻事件回放与分区顺序；SQS 缺少 cron、队列级限流等；进程内队列数据在内存、易丢失，「对于容错性高的任务可选」。
6. **QueueEvents vs Worker 本地事件**：「QueueEvents 强调约定，Worker 本地事件可以自定义」。
7. **FlowProducer vs 手动 add**：「FlowProducer 类似工作流，一次性完成整个任务；processor 里的 add 是人为调用，属于高度定制化工作流的一环」。
8. **重启不丢 + 投递语义**：靠 Redis 持久化特性；「投递语义意味着稳定性高、系统健壮性强」。

## 错点 / 待加固

- ① **pull vs push**：说成「把 Job 推送给设备网关」（实际 Worker 主动拉取；这正是解耦与背压的基础）。
- ② **`QueueEvents` 的角色**：说成「强调约定 vs 自定义」（实际是「跨进程事件流」vs「Worker 进程内事件」）。
- ③ **at-least-once**：把「不丢」绝对化，未答出 worker 崩溃后 active job 会被判 stalled 并**重新执行**，因此必须幂等。
- ④ 非 Node/TS 团队不该用（官方有 Python / Rust / Elixir / PHP / .NET 绑定）。
- ⑤ 进程内队列适用条件说反（应为「可容忍丢失」的任务）。
- ⑥ FlowProducer 的本质（原子依赖树 + waiting-children + 自动入队）未答出。

错点已写入 `state.json.errors`（append-only），并在 `notes/S01-概念模型与选型.md` 第 8 节展开成纠错稿。
